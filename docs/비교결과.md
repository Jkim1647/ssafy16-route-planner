## 해석

- **실행 흐름:** 세 조건 모두 같은 Tool 호출 수·같은 결과(카드 수)를 냈다. Planner·Worker 분리는 결과를 바꾸지 않고, 역할(planner/worker/logger)과 검증 단계가 실행 로그에 드러나게 했다.
- **재계획 횟수:** 재계획 상한(NF3004) 3회가 모드와 무관하게 지켜진다. S2는 거점 확장으로 모자라 수단 확장(택시 구간)까지 2회 후 통과, S3은 상한 3회(전날 출발)에서 고속버스 후보로 통과했다.
- **Worker LLM 비용:** 네 요청 모두 Worker LLM 호출 0회. 실패가 '고칠 수 있는 인자'를 가진 Tool(역·터미널 반경)에서 날 때만 LLM에 묻는데, 이번 실행에선 그런 실패가 없었다. 요청당 LLM 호출은 단일 모드와 같다(1~2회). 그래서 이 표로는 Worker가 개입했을 때 재계획 횟수·응답 시간이 어떻게 달라지는지는 판단할 수 없고, 개입 동작(반경을 넓혀 재시도·고정 인자 변경 거부)은 자동 테스트(`test_worker_retry_on_no_data`, `test_worker_cannot_change_fixed_args`)로만 확인했다.
- **검증(로깅 Agent):** 재계획 후반 패스의 warn은 `EXCESSIVE_REPLAN`(재계획 2회 이상)이다. 기록·진단 대상이고 재구성 트리거가 아니어서 무한 루프 없이 상한에서 멈춘다. 중복 호출·계획 외 호출이 생기면 1회 재구성한다(테스트 `test_verify_warn_triggers_one_rebuild`).
- **응답 시간:** 5~9초. 외부 API 결과는 캐시를 거치므로 반복 실행에서는 LLM 호출 시간이 대부분이다.

## 1일차(2026-11-18) 대비 달라진 점

| 요청 | 1일차 | 2일차 | 이유 |
|---|---|---|---|
| S1 | 카드 3 · Tool 16 | 카드 4 · Tool 17 | 행사 정보 Tool(`get_festivals`) 1회 추가, 순위 범주 '늦게 출발' 추가로 카드 최대 4 |
| S2 | 재계획 1 · 카드 2 | 재계획 2 · 카드 3 | 같은 날(11/21) 열차는 그대로. 거점 확장만으로는 통과 후보가 없어 수단 확장까지 갔다(접근 구간 대중교통·택시 소요가 바뀐 영향으로 추정 — 확인하지 못함) |
| S3 | 상한 3회 후 후보 없음 | 상한 3회 후 카드 4 | 고속버스 터미널 인식 수정 전에는 광주·강남 터미널 쌍을 못 찾아 버스 후보가 0이었다. 수정 후 4번째 쌍(광주→센트럴시티)에서 노선을 찾고, 전날 출발 단계에서 통과 |

처음 재실행 땐 S2가 후보 없음으로 나왔다. 원인은 이 스크립트가 실제 Google 캘린더를 읽어 그날 일정과 겹친 후보가 모두 빠진 것 — 스크립트에 로컬 캘린더를 고정하고 다시 돌렸다.

## 개선 이력 (이 실험으로 발견)

첫 실행(1일차)에서 S2(Worker LLM on)의 Worker LLM 호출이 15회, 로깅 Agent 판정이 `DUPLICATE_CALL` 다수였다. 원인은 (1) 재계획 때 같은 Tool·같은 입력을 다시 부르고 결과의 캐시 표시가 사라진 것, (2) 고칠 인자가 없는 열차 조회 실패에도 LLM에 물은 것. 실행 단위 결과 재사용(F3009)과 `TUNABLE` 규칙(조정 가능한 인자가 있는 Tool만 LLM 판단)을 추가해 Worker LLM 15회 → 0~1회, 중복 호출 판정 0건이 됐다.
