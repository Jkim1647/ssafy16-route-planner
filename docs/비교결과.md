## 해석

- **실행 흐름:** 세 조건 모두 같은 Tool 호출 수·같은 결과(카드 수)를 냈다. Planner·Worker 분리는 결과를 바꾸지 않고, 역할(planner/worker/logger)과 검증 단계가 실행 로그에 드러나게 했다.
- **재계획 횟수:** S2는 세 조건 모두 1회(거점 확장 후 통과), S3은 모두 상한 3회에서 멈추고 조건 조정을 되묻는다. 재계획 상한(NF3004)이 모드와 무관하게 지켜진다.
- **Worker LLM 비용:** 정상 경로(S1·S2·S7)에서 Worker LLM 호출은 0회다. 실패가 '고칠 수 있는 인자'를 가진 Tool(역·터미널 반경)에서 날 때만 1회 늘었다(S3: 고속버스 터미널 검색 결과 없음 → 반경 확대 판단). 요청당 LLM 호출은 단일 모드 대비 +0~1회.
- **검증(로깅 Agent):** S3 후반 패스의 warn은 `EXCESSIVE_REPLAN`(재계획 2회 이상)이다. 이 규칙은 기록·진단 대상이고 재구성 트리거가 아니어서 무한 루프 없이 상한에서 멈춘다. 중복 호출·계획 외 호출이 생기면 1회 재구성한다(테스트 `test_verify_warn_triggers_one_rebuild`).
- **응답 시간:** 3~9초. 외부 API 결과는 영구 캐시를 거치므로 반복 실행에서는 LLM 호출 시간이 대부분이다.

## 개선 이력 (이 실험으로 발견)

첫 실행에서 S2(Worker LLM on)의 Worker LLM 호출이 15회, 로깅 Agent 판정이 `DUPLICATE_CALL` 다수였다. 원인은 (1) 재계획 때 같은 Tool·같은 입력을 다시 부르고 결과의 캐시 표시가 사라진 것, (2) 고칠 인자가 없는 열차 조회 실패에도 LLM에 물은 것. 실행 단위 결과 재사용(F3009)과 `TUNABLE` 규칙(조정 가능한 인자가 있는 Tool만 LLM 판단)을 추가해 Worker LLM 15회 → 0~1회, 중복 호출 판정 0건이 됐다.
